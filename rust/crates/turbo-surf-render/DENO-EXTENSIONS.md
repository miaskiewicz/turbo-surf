# Portable official Deno extension JavaScript

The render crate embeds all 28 JavaScript modules declared by these named
Deno distributions:

| Rust alias | Package | Version | Upstream crate |
| --- | --- | --- | --- |
| `deno_web` | `turbo-surf-deno-web` | 0.290.1 | `deno_web` 0.290.0 |
| `deno_webidl` | `turbo-surf-deno-webidl` | 0.259.1 | `deno_webidl` 0.259.0 |
| `deno_crypto` | `turbo-surf-deno-crypto` | 0.273.1 | `deno_crypto` 0.273.0 (+ reviewed patch) |

The upstream archives' checksums are pinned in
`rust/release-deps/deno/source-pins.json`; the 0.x.1 distributions carry the same
JavaScript bytes as the earlier 0.x.0 distributions.

Nothing is vendored in this crate. Each 0.x.1 distribution exposes its exact
published JS as a compile-time library API generated by
`rust/release-deps/deno/prepare.py` (which checks the official declaration hash,
the ordered source inventory, every file's SHA-256/length/ASCII and the license
against `source-pins.json`):

```rust
deno_web::embedded_sources::{SourceKind, EmbeddedSource, EXTENSION, LICENSE,
                             LICENSE_SHA256, SOURCES}
```

(`deno_webidl::embedded_sources` and `deno_crypto::embedded_sources` alike;
`SOURCES` holds 26 / 1 / 1 entries in declaration order, each with `extension`,
`kind`, `specifier`, `code`, `sha256` and `bytes`). Crypto's Rust provider still
comes from its hardened package; no provider or op is replaced here. All embedded
JS bytes are unchanged from the published archives. The distributions ship the
complete upstream MIT license as `embedded_sources::LICENSE`; the root third-party
notices also carry the Deno attribution and full MIT text. WebIDL's unchanged
source also retains its `webidl-conversions` BSD-2-Clause header. The complete
inherited BSD text and pinned upstream source are included in this crate's root
`THIRD_PARTY_NOTICES.md` and the synchronized Python notice.

Deno core 0.412 records extension JS as `LoadedFromFsDuringSnapshot` paths rooted
at the dependency's compile-time `CARGO_MANIFEST_DIR`. Its own core bootstrap is
embedded, but the Web/WebIDL/Crypto extension modules are not. Loading those
paths in an installed wheel outside the original build container can fail even
when the same artifact worked on the build host. This is independent of glibc,
C++ exception flags, CPython abi3 and the Python license policy.

`deno_extension_sources::embed` validates every official extension's complete
ordered `js_files`, `esm_files`, `lazy_loaded_js_files` and
`lazy_loaded_esm_files` inventory against the distributions' `SOURCES` tables,
then replaces their source storage with the public `ExtensionFileSource::new`
static API over the embedded bytes. Missing, extra, duplicate, reordered or moved
specifiers fail before runtime creation. It never reads or falls back to the
recorded build-machine paths. WebIDL and Web then pass through the existing three
hash-checked private dense-array adapters; embedding does not bypass or change
their security boundary. There is no snapshot pipeline.

The reviewed pins stay in this crate: `src/deno_extension_sources_tests.rs`
carries `SOURCE_PINS` (specifier, SHA-256, byte length for all 28 modules) and the
license hash. `distribution_tables_match_the_reviewed_pins` hashes every embedded
module and license and requires both the distribution's own pins and these
reviewed pins to match, so a dependency update that changes any byte fails
`cargo test`. `rust/release-deps/deno/test_prepare.py` asserts that
`source-pins.json` and `SOURCE_PINS` agree. A dependency update requires
reviewing its complete declared source inventory and updating both.

Because the sources come from ordinary dependencies, normal Cargo packages and
Python source distributions need no outside-file references.

Relocation regressions and actual direct/sdist-rebuilt installed-wheel tests are
separate required validation. Build-host execution alone cannot prove the absence
of a dependency on source files that still happen to exist on that machine.
